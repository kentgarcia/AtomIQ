# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

AtomIQ is an offline-first nuclear-science learning app: Expo SDK 58, React Native 0.88, React 19, Expo Router (file-based, typed routes), strict TypeScript. Node `>=22.13` is required (the content tooling uses `node:sqlite`). Path alias: `@/*` → repo root.

## Commands

```bash
npm run start | android | ios | web   # all run sync-content first, then expo start
npm run typecheck                     # tsc --noEmit
npm run lint                          # expo lint (lint:fix = eslint . --fix)
npm run sync-content                  # refresh assets/ bundle + CONTENT_DB_VERSION only if out of date
npm run release:content               # status; --publish, --list, --restore <ver>, --record-update <id>
npm run validate:content              # question quality gate; run BEFORE sync-content
npm run content-studio                # web content editor on http://localhost:8787 (edits the master DB as a draft)
```

There is no umbrella `npm test`. Each gate is its own script, and tests use `node --test` on a single file, so run one with e.g. `node --no-warnings --test scripts/test-media-policy.mjs`. Check scripts: `check:icons`, `check:theme-colors`, `check:tab-bar`, `check:feed`, `check:sfx`. Test scripts: `test:icons`, `test:activity`, `test:theme`, `test:media`, `test:sfx`, `test:contrast`, `test:visuals`, `test:periodic`, `test:content`, `test:maze`, `test:content-db`, `test:releases`, `test:backups`, `test:studio`, `test:curriculum`, `test:curriculum-content`, `test:npc`, `test:avatar`, `test:shop`, `test:path-nodes`, `test:missions`, `test:claim-fx`, `test:feed`, `test:feed-ui`, `test:lecture`, `test:option-pop`, `test:stamp`, `test:stat-reveal`, `test:legal`, `test:platformer`, `test:story-map`. See `package.json` for the exact file each one runs.

Before handing off: `sync-content`, `typecheck`, `lint`, plus the check/test scripts relevant to what you touched (icons, theme colors, content, media, sfx).

Android release builds go through EAS (`eas.json`: `preview` = APK, `production` = AAB) or `./build-apk.sh`. `credentials.json` and `*.jks` are signing secrets and are gitignored.

## Architecture

### Content is a SQLite database, not TypeScript

All learner-facing content (units, path nodes, lessons and cards, the item bank, myths, MythBuster questions, mazes, encyclopedia) lives in **`content/database/content.db`**, the master and source of truth. `README.md` and `scripts/content-migration/ts-to-json.js` describe an older `content/*.ts → seed-sqlite` pipeline; the `content/*/index.ts` files are now thin facades over SQLite reads.

Pipeline (editing is a draft; a version only exists once you **publish**):

1. Edit the master DB with Content Studio (`npm run content-studio`, `tools/studio/app.mjs`). Saves are validated by the same rules as `validate:content`, recorded in history (`content/database/studio-history.db`, gitignored) and written straight to the master. Schema: `scripts/content-migration/schema.sql`. One-off, repeatable data fixes live in `scripts/content-migration/*.mjs`; they take a backup first (`backupBeforeScript`).
2. Publish from Studio's **Publish** button or `npm run release:content -- --publish --notes "…"`. This validates, takes a `pre-publish` backup, then writes `content/releases.json` (append-only ledger), `content/releases/<ver>.db.gz`, `content/shipped-ids.json` (only grows), `content/snapshot/*.json`, the bundled `assets/database/content.db` (with a `content_meta` table) and the `CONTENT_DB_VERSION` string in `services/content-db.ts`. Versions are semver (`1.4.0`); the working copy is `<last>+draft.<hash>`. The bump suggestion (patch = edits, minor = rows added/removed, major = a shipped id retired or `CONTENT_SCHEMA_VERSION` changed) can be raised but not lowered. Never edit the version constant or the ledger by hand.
3. `npm run sync-content` only rebuilds the bundle/constant when its metadata is out of date (`start*` and `postinstall` run it); it never creates a version. `npm run release:content` with no flags shows the current status; `--list`, `--restore <ver>` (as a draft) and `--record-update <eas-group-id>` manage releases.
4. At runtime `services/content-db.ts` (`ensureContentDatabase()`, awaited by `components/content/ContentGate.tsx` while the splash is up) copies the bundled DB into on-device storage when the version differs, via `content.next.db` → verify → swap with rollback (`services/content-db-core.ts` holds the pure decisions). `contentRepository` provides typed queries that hydrate JSON columns into the shapes in `content/types.ts`.

Backups (`content/backups/`, gitignored; optional mirror via `ATOMIQ_BACKUP_DIR`) are taken automatically each day, before publish/restore/scripts, and on demand from Studio → Backups. Shipped ids can't be renamed or deleted without a recorded retire reason. EAS production builds run `check:content-published` and fail on an unpublished draft (`ATOMIQ_ALLOW_DRAFT=1` overrides). Studio tests: `test:studio`, `test:releases`, `test:backups`, `test:content-db`.

Commit the content files together after a publish: both `content.db` files, `content/releases*`, `content/shipped-ids.json`, `content/retired-ids.json`, `content/snapshot/`. The `-wal`/`-shm` sidecars are gitignored.

Spec: `docs/LESSON_RESTRUCTURE_SPEC.md`. Explorer narrators are still to do. The learner's avatar uses the same art (`components/avatar/`): `avatar-core.ts` holds an `AvatarConfig` of ids (skin, hair, eyes, outfit...) plus the catalogs that resolve them to an `NpcSpec`, `Avatar.tsx` draws it in the square `avatar` crop of `NPC_VIEWBOX`, and `user_profile.avatar_url` stores `avatar:v1:{ids}` (old photo names read as the default design). There are two starting designs now (`STARTER_AVATARS`: `DEFAULT_AVATAR` and `BUN_AVATAR`, hair in a bun and a pink sweater), picked once on onboarding's profile step and saved as `avatar_url`; nothing else lets the design change yet; the picture behind the figure is a paint (`background`, a solid colour) plus an optional `pattern` (35 vector wallpapers, ids are words like `atomlab` and `polka`: pure data in `pattern-art.ts`, `PATTERN_DEFS` with a name, a set of one-colour 24-box pictures (the teachers' cover pictures plus a few shapes of their own) and a `stagger` or `dense` layout on a 96-unit tile that repeats without a seam; `PatternLayer.tsx` draws whole tiles in one Svg, white, and the layer is at 50%, so the shapes are a lighter tone of the paint and the paint is never darkened; `node scripts/render-avatar-patterns.mjs <dir>` makes a contact sheet; an avatar saved with an old `pNNN` tile id reads as no pattern; to add one, add a `S(...)` line to `PATTERN_DEFS` and never reuse a shipped id); a future picker only chooses ids from `AVATAR_OPTIONS` and saves `serializeAvatar(config)`, no new drawing code (`test:avatar`). The Shop (`app/shop.tsx`, opened from the Profile header; data in `components/shop/shop-core.ts`, `test:shop`) is UI only so far: category tabs (Hair, Eyes, Outfits, Skin, Paints, Patterns), a dashed item grid and a preview on the big avatar, with `SHOP_ITEMS` empty. An item is one avatar choice plus a diamond price; buying and owning (a user-state table) are not built. The visual and UX redesign of the lesson screens (brand pass) is specified in `docs/LESSON_VISUAL_SPEC.md`. Content tables (schema v2, between the `curriculum-v2` markers in `schema.sql`): `units`, `objectives`, `lessons`, `path_nodes`, `items`, `lesson_cards`, `content_references` (+ `unit_references`, `lesson_references`), `content_translations` (empty, for localization). The DB holds values only; every interaction is a hardcoded component in `components/lesson/cards/`. Option buttons (`OptionRow`, `PictureOption`, over `OptionSurface` in `cards/shared.tsx`) pop when they become selected or correct, measured frame by frame from a reference clip: the colour flips at once, the face shape (fill and border, a layer apart from the label, which never scales) squashes, springs up tall, hangs on a slab of lip while a slanted band of light accelerates across and two corner sparkles twinkle, falls stretched, lands squashed, hops a little and settles (keyframes in the framework-free `cards/option-pop-core.ts`, `test:option-pop`; reduced motion keeps only the colour change); an option is the same size in every state (the right/wrong mark has a reserved slot, and a choice's "why not this one" note is said in the feedback sheet, not inside the option), and a wrong option shakes as a whole, lip included; a pop cut short by the next state (an instant-graded answer is selected for one frame, then wrong; a pick moved to another option) is put at rest, never left frozen half way (`popAction` in `option-pop-core.ts`). Start or Review pushes `/lesson/<id>?autostart=1&resume=continue|again`, which skips the lesson screen's own preview (stage `boot`, then the run; a lesson left half way is asked about on the map first, from `savedPercent` in `LessonPreviewData`, drawn INSIDE the preview layer's modal (`ResumeLessonOverlay`: `ModalCard` over its own scrim; never a second `Modal` opened over the preview, which does not reliably show, so Review did nothing); the lesson screen falls back to its own preview if nothing has started 2.5 s after it loaded, never a blank page), while the other node kinds still push their `practice` route (which fades in), with its title (no status line: the node shows that) and a button; the bubble wears its unit's colours, and the locked grey on a locked node; it opens under the node, or above it when there is no room below (by the navbar or under the lesson card), and scrolls the map a little when neither side has room (`chooseBubbleSide` in `node-bubble-core.ts`); the nodes fake 2.5D (elliptical face on a side band, the map itself stays flat); `node scripts/render-node-glyphs.mjs <dir>` draws a contact sheet. ### Atom Maze platformer (story mode)

A side-scrolling replacement for the old maze. Games > Atom Maze opens a level map (`app/explorer/story.tsx`: worlds of five levels, the tutorial, then Unit 1 (one lesson a level, an evergreen forest) and Unit 2 (the desert; later units add five each), listed in `components/platformer/story-levels.ts` (`STORY_LEVELS`, `STORY_WORLDS`) and drawn as a winding road of the lesson map's own pucks and speech bubble under a banner per world in the unit's colour, maths in `story-map-core.ts`, `test:story-map`; progress in the `story_progress` table via `services/story-progress.ts`, unlock and lesson-recommendation rules in the framework-free `story-core.ts`); a level plays in `app/explorer/platformer.tsx?level=<id>` (spec `docs/PLATFORMER_SPEC.md`): run and jump, touch an enemy to battle it with a FIXED question from the level's unit (`story-battle-core.ts`, `story-questions-core.ts`, `services/story-questions.ts`; ids of bank items, checked against `content.db` by the tests), reach the flag (shut while the boss lives, last level only); missed questions lead to "Review these lessons" on the result card. The level's small moments are pure timelines in `world-fx-core.ts` (blocks jump and glint, coins and hearts pop out, bricks break into pieces, coins pop when picked up, checkpoint and goal flags pop up when raised, signs rock and show a typed bubble that pops out of them; `WorldFx.tsx`, `SignBubble.tsx`); beating the boss plays a celebration (`boss-victory-core.ts`, `BossVictory.tsx`: shudder, swell, burst, cheer, confetti, "<Boss> defeated!", the camera visits the flag as it opens) and only then opens the flag. The goal is a door (two tiles; `F` in a level file): touching it plays the end on the map, not a card (`exit-core.ts`, `ExitView.tsx`: the camera zooms on the door, it opens, the hero walks in and it shuts, the title is stamped, the stars pop out over it one by one, then `ResultPanel.tsx` fades in at the bottom, written straight onto a dark gradient with icon-only buttons; out of hearts lays the hero down (one still frame, crossed-out eyes) and zooms instead). Footsteps, landings and the hero's thud follow the level's ground (the jump is one Mario-style hop on every ground, `game.jump`) (`platformer-sfx-core.ts`; cues `game.step-<ground>-left`...), with a checkpoint sound and fireworks at the finish. Speech-bubble emotes (Kenney's Emotes, `emote-core.ts`, `EMOTE_SPRITES`, baked by `scripts/bake-emotes.mjs`) pop over the hero and enemies for what happens (contact, right and wrong answers, lost hearts, keys, locks, checkpoints, a long idle); the rules are in `emotesForEvent` / `emotesForAnswer`. A level opens with a loading screen (pictures preloaded, questions loaded, world mounted under it), then Shrodi walks in from the left, gets ready and the mission shows at the top (`entrance-core.ts`, `LoadingScreen.tsx`, `MissionBanner.tsx`, `preload.ts`); there is no start card. Stars come from the points (`starsFor`: flag 1, 60% of the best score 2, 85% 3) and the timer (seconds outside battles) is only kept as the best time (`story_progress.best_time`). Levels 1 to 5 are the tutorial (readable signs, each adds mechanics: blocks and planks, springs, moving platforms with keys and locks), and each unit has five levels of its own; Unit 1's add gems, conveyor belts, saws and lava, one new thing per level (its first sign explains it; its other two signs are a short lesson discussion that teaches around the level's questions without giving answers away), and a sign's speech bubble shows a picture of what it is about (`SignIcon.tsx`, `signs: [{ text, icon }]`; on the map a sign is always the signpost tile); Unit 2's add bridges of logs and gem blocks (levels 11 and 12; 13 has islands that halve, 14 steps up and down, 15 everything and the boss; legend in `LevelDef` of `platformer-core.ts`). Smoothness rules (spec section 5e): `PlatformerWorld` and its pieces are `memo`s; drifting decorations read the clock through `stepped()` (`world-fx-core.ts`) so their style is constant between steps; no `ShineSweep` or other looping clock per gem or block; `fillFrame` parks far-away enemies and platforms at `PARKED_PX`; chunk pictures are cached (`chunkItems`). The rules are framework-free and tested (`npm run test:platformer`): `components/platformer/platformer-core.ts` (ASCII level format, physics in tiles, enemies, battle outcome, score), `platformer-levels.ts`, `battle-core.ts` (questions over `services/atom-maze-progression.ts`), `platformer-view.ts` (tile pictures, visible chunks, the per-frame pixel array). The screen steps the core at a fixed 1/60 s from a `requestAnimationFrame` clock and writes one array shared value per frame that every sprite reads in `useAnimatedStyle` (no React render per frame). Art is Kenney's New Platformer Pack (CC0), kept in `tools/platformer-art/` (outside the app bundle: `Vector/` SVGs are the editable sources, `Sprites/` the original PNGs, plus the licence; the rest of the pack was removed); what the game uses is moved into `assets/images/platformer/<group>/` (backgrounds, enemies, tiles, props, hud, characters) and required by hand in `components/platformer/sprites.ts`. The hero is Shrodi, one 62-frame sprite sheet (256 px cells drawn on a 128 canvas): the body is copied from the Kenney character's own poses (limbs and torso, helmet and face removed, torso painted as a white coat stretched taller, orange hands and arms, legs close together, all behind the coat) with Shrodi's real head and tail on it and Kenney's #353541 stroke as one outline round the whole figure; baked by `node scripts/bake-shrodi-hero.mjs` (source `Vector/Characters/shrodi_sheet.svg`, picture `Sprites/Characters/character_shrodi_sheet.png`). The clips (idle with a fidget, a 4-frame walk driven by distance walked, jump, land, hit, cheer) and which frame to show are in the framework-free `hero-anim-core.ts`, drawn by `HeroSprite.tsx` and the world's `Hero`. A battle is on the map, not a screen of its own: touching an enemy freezes the world and zooms the whole picture in on the pair (`battle-fx-core.ts`: the zoom plan and the attack and hurt timelines, all framework-free and tested), the question rises over the bottom with TWO options (`BattlePanel.tsx`, the lessons' `OptionRow`s; a multiple choice question keeps its right answer and one wrong one), and the answer is a fight: a right one is an attack (the hero leaps, the enemy is thrown back (no flash on a beaten enemy: only the hero flashes, when hurt), a burst and impact lines, a zoom punch), a wrong one a hurt (the enemy lunges, the hero flashes red and is thrown back, the picture shakes, a red wash, a heart breaks off); the moves, squashes and flashes ride in the per-frame array and the effects are in `BattleFx.tsx`. The map fills the whole screen (no header; sky above, dirt below fading to black behind the controls) under a game HUD (`GameHud.tsx`: the lessons' own progress bar on the top row with checkpoint flags and the goal flag on it and a bare filled white pause icon on its right that opens `PauseDialog.tsx`; below it the hearts with the pack's coin and digit sprites under them, both popping on change). Pictures there are double-size (`node scripts/bake-platformer-sprites-2x.mjs` after adding a `require` to `sprites.ts` draws it from the pack's SVG) and Shrodi's sheet is 256 px a frame, so zoomed battles stay sharp; ground tiles overlap by a pixel so no seams show when the view is scaled. The first time the hero comes within 7 tiles of the boss a cinematic plays (`boss-intro-core.ts`, `BossIntro.tsx`: letterbox bars, a scroll to the boss and a zoom in, a roar with a slam, shake and burst while its name is stamped on the bottom bar, then a scroll back to the hero; it always plays through, no skip; reduced motion skips it). The backdrop is a stack (`backdropStack`, `BIOMES`): solid sky, clouds, a biome picture (hills, trees, desert or mushrooms, `color` or `fade`) whose bottom sits on the ground line so it shows above the ground tiles, and below a `color` biome a solid fill of its ground to the bottom edge. ### Two separate databases / stores

- **Content DB** (read-only, re-seeded on version bump): `services/content-db.ts`.
- **User-state DB** (writable, local-first): `services/database.ts` creates tables from `services/local-first/schema.ts`, with sync metadata prepared for a future Supabase sync. It migrates by adding columns in code (`ensureTableColumns`), not by migration files. Profile, XP/streaks, missions, bookmarks and explorer progress live here, accessed through `services/StorageContext.tsx`, `services/storage.ts`, `services/explorer-storage.ts`, `services/missions.ts`, and `services/activity-*.ts`.
- **AsyncStorage** (`STORAGE_KEYS` in `services/storage.ts`, all prefixed `@atomiq:`) holds lightweight preferences only.

### Theme system (enforced by scripts)

- Styles are theme-dependent: define them with `createStyles((theme) => ({...}))` from `@/theme` and call the result inside the component with the current theme. Do **not** use a static module-level `StyleSheet.create` with colors.
- Use semantic theme color roles from `theme/themes.ts` and tokens from `theme/tokens.ts`. `npm run check:theme-colors` fails on hardcoded neutral surface/text/border colors, duplicated light/dark palettes, and alpha applied to literal colors (use `withAlpha(themeColor, a)`).
- Genuinely invariant colors (e.g. Atom Maze artwork) need either a `FILE_EXCEPTIONS` entry in the check script or an inline `// theme-allow: <reason>` comment. Both must also be registered in `docs/THEME_EXCEPTION_REGISTER.md`.
- Every modal is a `<ModalDialog>` (`components/ui/modal-dialog.tsx`, card in `modal-card.tsx`; the Edit Profile modal is the reference): yellow header band with a white round close button holding a plain X (`CloseGlyph`, no circle of its own), 20 dp side padding, as tall as its content with the body scrolling only past the screen-sized `maxHeight`, and the actions in the pinned `footer`. The main button is `<ModalButton>` (the header's yellow, `size="large"`); other actions use `ModalSecondaryButton` or another variant (`destructive` for a delete). Do not hand-roll a `Modal` + card. Bottom sheets (`MeetSheet`) are the one exception.
- Cards are `components/ui/card.tsx` (3D: border plus lip) and buttons are `components/ui/button.tsx`; use them rather than hand-rolled borders. Lesson figures use the fixed Duolingo-style palette in `components/lesson/visual/duo-palette.ts` (EX-11).
- Layout primitives (`components/layout/: `ScreenFrame`, `ResponsiveContainer`, `ResponsiveGrid`, `tab-bar-inset`) handle safe areas, tablets and tab-bar clearance. `check:tab-bar` verifies that scrollable screens clear the tab bar. Every top-level page uses the one header `ScreenHeader` (`components/layout/screen-header.tsx`, with `HeaderButton` and `useHeaderBorder`): a big left title, or a centred title between a left and a right slot when it has `onBack`/`left`; it sits above the scrolling body, adds the top safe-area inset itself and gets the tab bar's 2 dp border once the body scrolls.

### Icons

Use `components/ui/icon.tsx`, never `iconsax-react-native` directly. It resolves names through `components/ui/icon-registry.ts` (reviewed aliases plus a visible fallback). Icon names also appear in DB content, so `npm run check:icons` validates both source and the bundled DB. Where the library has nothing that says the thing, AtomIQ draws its own in the same Iconsax Bold style (24 grid, solid rounded shapes, details cut out, a faded 0.4 layer for a "not" icon): `components/ui/custom-icons.ts` is pure data with names that start with `Aq` (`AqAtom`, `AqNucleus`, `AqWave`...), `Icon` draws them like any name (only Bold exists; absolute path commands only, so `test:custom-icons` can check the bounds), and `node scripts/render-custom-icons.mjs <dir>` makes a contact sheet to look at. Add a new one there, not by picking the nearest library icon.

### Media policy

All sound effects are cues in one catalog (`services/sfx-core.ts`, framework-free, `test:sfx`; the runtime is `services/sfx.ts`; files are 16-bit mono WAV in `assets/sfx/<group>/`; spec `docs/SFX_SPEC.md`): call `playSfx("group.name")` from the component that owns the moment, never `require` an effect or call `expo-audio` (`npm run check:sfx` fails on it, and on a WAV that is not 16-bit mono 44.1 kHz). A new sound is a file, an `SFX_FILES` entry, a cue row and a `require` in `sfx.ts`; `node scripts/normalize-sfx.mjs` levels the files. `assets/sfx/kent-sfx/` is the unused, gitignored rest of the library. Read Aloud and music go through one runtime with them: `services/media-core.ts` (framework-free, unit-tested state machine and gates) and `services/media.ts` (runtime and lifecycle). Screens must use `<ReadAloudButton>` and the `use-read-aloud` hooks, and never call `expo-speech` or `expo-audio` directly. Details are in `docs/MEDIA_POLICY.md`.

## Other notes

- **Lesson cascade (built, unseen on a device):** lessons use the onboarding's arrival: his bubble pops (and types in lectures; the teacher himself stands still, no pop), the title and question rise, the options rise one by one with a soft tick (`components/motion/cascade-fx.ts`, `cascade-context.tsx` provided by `LessonRun`, `use-cascade-sfx.ts`; spec and what is left: `docs/LESSON_CASCADE_SPEC.md`).

- Expo Go is fine for iteration, but verify safe areas, back handling, keyboard, TTS, fonts and audio on a release-like Android build.
- `.opencode/` and `.openidea/` are tooling state. `.opencode/plugin/atomiq-content.ts` is an OpenCode plugin that talks to the Content Studio HTTP API.
