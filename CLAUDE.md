# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

AtomIQ is an offline-first nuclear-science learning app: Expo SDK 58, React Native 0.88, React 19, Expo Router (file-based, typed routes), strict TypeScript. Node `>=22.13` is required (the content tooling uses `node:sqlite`). Path alias: `@/*` → repo root.

## Commands

```bash
npm run start | android | ios | web   # all run sync-content first, then expo start
npm run typecheck                     # tsc --noEmit
npm run lint                          # expo lint (lint:fix = eslint . --fix)
npm run sync-content                  # refresh assets/ bundle + CONTENT_DB_VERSION only if out of date
npm run release:content               # status; --publish, --list, --restore <ver>, --record-update <id>
npm run validate:content              # question quality gate; run BEFORE sync-content
npm run content:sync                  # source files (content/source/**.atomiq) -> DB: dry run; --apply writes; see "Content source files" below
npm run check:source                  # exit 1 if the source files and the DB differ (also a publish gate)
npm run content:export | content:format | content:migrate   # DB -> files, canonical rewrite, format-version migration
npm run content-studio                # web content editor on http://localhost:8787 (edits the master DB as a draft)
npm run publisher                     # slide viewer + PNG download for publication material on http://localhost:8788 (tools/publisher; slides are hardcoded in public/slides.js)
```

## Architecture

### Content is a SQLite database, not TypeScript

All learner-facing content (units, path nodes, lessons and cards, the item bank, myths, MythBuster questions, encyclopedia) lives in **`content/database/content.db`**, the master and source of truth. `README.md` and `scripts/content-migration/ts-to-json.js` describe an older `content/*.ts → seed-sqlite` pipeline; the `content/*/index.ts` files are now thin facades over SQLite reads.

Pipeline (editing is a draft; a version only exists once you **publish**):

1. Edit the master DB with Content Studio (`npm run content-studio`, `tools/studio/app.mjs`). Saves are validated by the same rules as `validate:content`, recorded in history (`content/database/studio-history.db`, gitignored) and written straight to the master. Schema: `scripts/content-migration/schema.sql`. One-off, repeatable data fixes live in `scripts/content-migration/*.mjs`; they take a backup first (`backupBeforeScript`). **Tables owned by source files are edited in `content/source/` and built with `npm run content:sync`; for the rest, agent edits go through `npm run content:edit` (`scripts/content-edit.mjs`), not a new migration script**: a patch (JSON, or a `.mjs` that exports the operations) of `update`, `replace` (text find and replace in a column), `insert` and `delete` runs as ONE transaction with ONE validation pass (`applyBatch` in `scripts/lib/content-store.mjs`), recorded in the same history as Studio (source `cli`), with no server. Without flags it is a dry run on a copy that prints every before and after and the validation result; `--apply` takes a backup (skipped when the newest backup already holds this exact content), writes, and runs in parallel only the tests that read the touched tables (`scripts/lib/content-checks.mjs`; `--no-verify` skips). An operation that matches no rows is an error (typo guard; `optional: true` to allow, `expect: n` to assert a count), a shipped id cannot be renamed and its delete needs `retire`. A batch also fails on any NEW validation error anywhere in the database, not only on the rows it edits (a chat thread is just nodes pointing at each other with `replies[].next`, and a lesson needs exactly one intro line, so deleting or repointing one row breaks rows it never touched; Studio's per-row check lets those through until `validate:content`), so delete and repoint in the same patch. `content:edit -- get <table> [--pk a,b] [--q text] [--where col=val] [--cols a,b]` and `-- sql "SELECT ..."` read the master. For chats, `content:edit -- thread <teacher>` lists that teacher's stories (first node, trigger, node count) and `-- thread <teacher> <story>` (first node id, trigger, or part of the title) returns only that story's nodes in reading order, marking any node another story also uses (`also_in`): fetch a story, not a teacher. Keep `scripts/content-migration/*.mjs` for edits that need real logic or that regenerate from a source file (`sync-unit.mjs`, `apply-npc-voices.mjs`); remember a DB edit does not change `curriculum/unit-N.mjs` or `npc-roster.ts`, and re-running their sync overwrites it (`test:content-batch`).
2. Publish from Studio's **Publish** button or `npm run release:content -- --publish --notes "…"`. This validates, takes a `pre-publish` backup, then writes `content/releases.json` (append-only ledger), `content/releases/<ver>.db.gz`, `content/shipped-ids.json` (only grows), `content/snapshot/*.json`, the bundled `assets/database/content.db` (with a `content_meta` table) and the `CONTENT_DB_VERSION` string in `services/content-db.ts`. Versions are semver (`1.4.0`); the working copy is `<last>+draft.<hash>`. The bump suggestion (patch = edits, minor = rows added/removed, major = a shipped id retired or `CONTENT_SCHEMA_VERSION` changed) can be raised but not lowered. Never edit the version constant or the ledger by hand.
3. `npm run sync-content` only rebuilds the bundle/constant when its metadata is out of date (`start*` and `postinstall` run it); it never creates a version. `npm run release:content` with no flags shows the current status; `--list`, `--restore <ver>` (as a draft) and `--record-update <eas-group-id>` manage releases.
4. At runtime `services/content-db.ts` (`ensureContentDatabase()`, awaited by `components/content/ContentGate.tsx` while the splash is up) copies the bundled DB into on-device storage when the version differs, via `content.next.db` → verify → swap with rollback (`services/content-db-core.ts` holds the pure decisions). `contentRepository` provides typed queries that hydrate JSON columns into the shapes in `content/types.ts`.

Backups (`content/backups/`, gitignored; optional mirror via `ATOMIQ_BACKUP_DIR`) are taken automatically each day, before publish/restore/scripts, and on demand from Studio → Backups. Shipped ids can't be renamed or deleted without a recorded retire reason. EAS production builds run `check:content-published` and fail on an unpublished draft (`ATOMIQ_ALLOW_DRAFT=1` overrides). Studio tests: `test:studio`, `test:releases`, `test:backups`, `test:content-db`.

Commit the content files together after a publish: both `content.db` files, `content/releases*`, `content/shipped-ids.json`, `content/retired-ids.json`, `content/snapshot/`. The `-wal`/`-shm` sidecars are gitignored.

### Content source files (text is the master of what it owns)

Spec: `docs/features/CONTENT_SOURCE_SPEC.md` (read it before touching authored prose; user guide in `content/source/README.md`). Some tables are OWNED by `.atomiq` text files in `content/source/`, built into `content.db` by `npm run content:sync` (dry run by default; `--apply` takes a backup, writes in one `applyBatch` transaction with one validation pass and then runs the tests that read the touched tables; `--check` is the read-only comparison; `--retire "<reason>"` is needed to delete a shipped id; `--force` overwrites database changes that are not in the files). The files are the master and the DB is a build artifact; the app still reads SQLite and never reads the files. Owned so far: chat (`chat_nodes`, `chat/<npc>/`), characters (`npcs`, `npc_lines`, `characters/`), feed (`feed_templates`, `feed/`), blog (`blog_*`, `blog/<unit>/`), references (`content_references`, `reference/sources/<kind>.atomiq`), the AtomDex (`encyclopedia_entries`, one file per entry, `reference/encyclopedia/<category>/<id>.atomiq`), myths (`reference/myths/<category>.atomiq`), Myth Buster questions (`games/mythbuster/NNN-<difficulty>.atomiq`), unit statements (`units/<unit>/statements.atomiq`) and the phone's data: Scanner targets (`phone/scanner/`), Safety cards (`phone/safety/`) and Map sites (`phone/map/sites.atomiq`) with their reference links. Their seeds (`add-scan-targets`, `add-safety-and-map`, `add-unit-statements`, the glossary scripts) are retired in `scripts/content-migration/legacy/`; `sync-unit.mjs` and `unit-1-concept-pass.mjs` still write `content_references` until phase 5, so run `npm run content:export -- references --force` after them (and copy the change into the file). A sync inserts parents before children and deletes in reverse across adapters (`orderOps`; `OWNED_ADAPTERS` lists parents first). Owned tables are listed in `OWNED_ADAPTERS` (`scripts/lib/content-source/owned.mjs`): `npm run content:edit` and any new migration script must NOT write them (the CLI refuses; a write behind the files' back shows as "drift" on the next sync via `content/source/.state.json`). The core (`scripts/lib/content-source/core/`: parser, writer, value types) is generic and format-versioned; a table is an adapter (`adapters/*.mjs`, data: record keyword, columns and their types, layout) over the shared engine, and the lossless `default` adapter exists for every table. Prose is always indented 4 spaces and structure never is, so text needs no escaping; unknown keys, tabs, trailing spaces and duplicate ids are errors with `file:line`. Positions are derived from file order and never written. Paths are `content/source/<domain>/<owner>/NNN-<id>.atomiq` (spec section 6); `content:format` rewrites files in canonical form keeping comments (`--paths` renumbers). `content:migrate` brings files up to a new format version and refuses unless the rows read back identical. Retired seeds live in `scripts/content-migration/legacy/` and refuse to run. Tests: `test:source`, `test:source-sync`, `test:source-adapters`; golden files in `scripts/golden/content-source/`.

### XP rules

All of them are in the framework-free `services/xp-core.ts` (`test:xp`); change numbers there only. The first time always pays in full: a lesson its `xp_reward`, practice 20 and checkpoint 60 (`app/practice/[id].tsx`), an Atom Maze level's first win `ATOM_MAZE_FIRST_XP` (40). Every repeat pays `repeatXp` (10%, at least 1): `completeNode` does it for a replayed node (and logs it in `daily_activity`, no new lesson count, no feed post), the platformer pays it from `saveStoryResult`'s `firstWin` (`SavedResult`; a lost run pays nothing, the result panel shows "First win: +N XP"). Myth Buster has no first-time reward, only a repeat reward and the smallest in the app (`MYTHBUSTER_MAX_XP`: Quick 1, Challenge 2, Endless 5, since a round is about a fifth of a lesson's time): Quick and Challenge scale with the share answered right, Endless with the score (`ENDLESS_FULL_SCORE`, at least 1 for any score); paid once by an effect on the results screen. `services/game-xp.ts` (`awardGameXp`) adds a game's XP through `addXP` and never throws. `addXP` (`StorageContext`) is the one place that also counts every XP gain (lessons, games, quests, facts, the tour) in `daily_activity.xp_earned`, which is what the weekly ranking adds up: never log `xp_earned` beside an `addXP` call. Rivals in that ranking (`rank-core.ts`: `MIN_RIVAL_PACE`, `RIVAL_PACE_FACTOR`, habit and luck ranges) work slightly harder than the learner's usual week. The daily login quest counts once per calendar day (the saved last-active date, not the in-memory flag, so restarts do not repeat it). Quests: daily login, lesson, Myth Buster, fact; weekly login, lessons (a passed practice or checkpoint counts as a lesson), Myth Buster, Atom Maze levels (`maze`, a won level), facts. The daily chest needs every daily quest claimed, the weekly one any 3 (`CHEST_QUESTS_NEEDED`, `chestNeeded` in `missions-core.ts`).

### Theme system (enforced by scripts)

- Styles are theme-dependent: define them with `createStyles((theme) => ({...}))` from `@/theme` and call the result inside the component with the current theme. Do **not** use a static module-level `StyleSheet.create` with colors.
- Use semantic theme color roles from `theme/themes.ts` and tokens from `theme/tokens.ts`. `npm run check:theme-colors` fails on hardcoded neutral surface/text/border colors, duplicated light/dark palettes, and alpha applied to literal colors (use `withAlpha(themeColor, a)`).
- Genuinely invariant colors (e.g. Atom Maze artwork) need either a `FILE_EXCEPTIONS` entry in the check script or an inline `// theme-allow: <reason>` comment. Both must also be registered in `docs/critical/THEME_EXCEPTION_REGISTER.md`.
- Every modal is a `<ModalDialog>` (`components/ui/modal-dialog.tsx`, card in `modal-card.tsx`; the Edit Profile modal is the reference): yellow header band with a white round close button holding a plain X (`CloseGlyph`, no circle of its own), 20 dp side padding, as tall as its content with the body scrolling only past the screen-sized `maxHeight`, and the actions in the pinned `footer`. The main button is `<ModalButton>` (the header's yellow, `size="large"`); other actions use `ModalSecondaryButton` or another variant (`destructive` for a delete). Do not hand-roll a `Modal` + card. Bottom sheets (`MeetSheet`) are the one exception.
- Cards are `components/ui/card.tsx` (3D: border plus lip) and buttons are `components/ui/button.tsx`; use them rather than hand-rolled borders. Lesson figures use the fixed Duolingo-style palette in `components/lesson/visual/duo-palette.ts` (EX-11).
- Layout primitives (`components/layout/: `ScreenFrame`, `ResponsiveContainer`, `ResponsiveGrid`, `tab-bar-inset`) handle safe areas, tablets and tab-bar clearance. `check:tab-bar` verifies that scrollable screens clear the tab bar. Every top-level page uses the one header `ScreenHeader` (`components/layout/screen-header.tsx`, with `HeaderButton` and `useHeaderBorder`): a big left title, or a centred title between a left and a right slot when it has `onBack`/`left`; it sits above the scrolling body, adds the top safe-area inset itself and gets the tab bar's 2 dp border once the body scrolls.

### Icons

Use `components/ui/icon.tsx`, never `iconsax-react-native` directly. It resolves names through `components/ui/icon-registry.ts` (reviewed aliases plus a visible fallback). Icon names also appear in DB content, so `npm run check:icons` validates both source and the bundled DB. Where the library has nothing that says the thing, AtomIQ draws its own in the same Iconsax Bold style (24 grid, solid rounded shapes, details cut out, a faded 0.4 layer for a "not" icon): `components/ui/custom-icons.ts` is pure data with names that start with `Aq` (`AqAtom`, `AqNucleus`, `AqWave`...), `Icon` draws them like any name (only Bold exists; absolute path commands only, so `test:custom-icons` can check the bounds), and `node scripts/render-custom-icons.mjs <dir>` makes a contact sheet to look at. Add a new one there, not by picking the nearest library icon.

### Media policy

All sound effects are cues in one catalog (`services/sfx-core.ts`, framework-free, `test:sfx`; the runtime is `services/sfx.ts`; files are 16-bit mono WAV in `assets/sfx/<group>/`; spec `docs/features/SFX_SPEC.md`): call `playSfx("group.name")` from the component that owns the moment, never `require` an effect or call `expo-audio` (`npm run check:sfx` fails on it, and on a WAV that is not 16-bit mono 44.1 kHz). A new sound is a file, an `SFX_FILES` entry, a cue row and a `require` in `sfx.ts`; `node scripts/normalize-sfx.mjs` levels the files. `assets/sfx/kent-sfx/` is the unused, gitignored rest of the library. Read Aloud and music go through one runtime with them: `services/media-core.ts` (framework-free, unit-tested state machine and gates) and `services/media.ts` (runtime and lifecycle). Screens must use `<ReadAloudButton>` and the `use-read-aloud` hooks, and never call `expo-speech` or `expo-audio` directly. Details are in `docs/critical/MEDIA_POLICY.md`.

## Other notes

- **Performance, animation and sound across devices (phase 0 and the sound seam built, unseen on a device):** `docs/features/PERFORMANCE_AND_SOUND_SPEC.md` (read section 12 first, the maintenance runbook; device runs in `docs/qa/PERF_AND_SOUND_PASS.md`). `services/sfx.ts` is engine-agnostic: gates, scheduler and the outcome log `sfx-diag.ts`, then a backend from `pickBackend` (`sfx-backend-core.ts`, pure, tested): `sfx-backend-audio-api.ts` on Android when the module loads, `sfx-backend-expo-audio.ts` everywhere else; screens warm sounds by set (`SFX_SETS` in `sfx-core.ts`, `useSfxSet("lesson-run")`; every cue must be in a set, `test:sfx` checks), `EXPO_PUBLIC_SFX_BACKEND` forces an engine, and the perf probe (Home's bolt button, `components/dev/Perf*`, present in dev builds and in `preview` via `EXPO_PUBLIC_PERF_PROBE=1`) shows frames and why a cue was or was not heard. The device tier (`services/device-profile-core.ts`, `useMotionBudget`) sets only how fast decorative idle loops run, the share of burst stars and the `expo-audio` player cap, never the design; every progress bar uses `useFillStyle` / `useFillPxStyle`, never an animated `width`. The Reanimated static flag `ANDROID_SYNCHRONOUSLY_UPDATE_UI_PROPS` is on (root `package.json`, `reanimated.staticFeatureFlags`; a build-time setting: a native rebuild, invisible in Expo Go) so animated opacity and transform reach Android views without a shadow-tree commit per frame; if touch targets or the tutorial's lit holes misbehave on Android, that flag is the first suspect (docs/qa/PERF_AND_SOUND_PASS.md §3b). No bundled effect may be shorter than `MIN_SFX_MS` (50 ms, `sfx-core.ts`; `check:sfx` fails on one that is, `node scripts/pad-short-sfx.mjs --apply` pads with silence and fixes its `SFX_FILES` entry): the audio-api decoder could not decode files under about 30 ms on the first Android dev build. `react-native-audio-api` is pinned (1.0.1) and installed WITHOUT its Expo plugin (it adds foreground-service and background-audio entries): do not add the plugin. Three facts to keep: (1) the owner can test the iPhone **only in Expo Go** (dev JS bundle, never a performance or sound verdict; use `expo start --no-dev --minify` for timing) and Android as a preview APK; (2) the sound plan is a **split**: `react-native-audio-api` on Android only (needs a development build, cannot run in Expo Go, its `require` must stay guarded so a missing module never silences the app) and `expo-audio` on iOS and in Expo Go, both behind one `SfxBackend` seam so `playSfx` and its call sites never change; the spec's phase 0 spike decides whether the new engine is adopted at all; (3) every performance fix is measured first (the probe and `sfx-diag` in the spec's phase 0), and hypotheses in that spec are readings of the code until a number confirms them.

- **Animation level (Settings > Animations):** Max (everything, as designed), Reduced (what the learner causes still plays; nothing runs on its own and bursts are halved) and Disabled (no animation). Pure rules in `components/motion/motion-level-core.ts` (`test:motion-level`), the saved choice in `services/motion-level.ts` (`STORAGE_KEYS.MOTION_LEVEL`; unset means max, or reduced on a `low` device tier; `useMotionLevel`, loaded once by `app/_layout.tsx`). Always use `useReducedMotion` and `useIdleStill` from `components/motion/use-reduced-motion.ts`, NEVER `useReducedMotion` from `react-native-reanimated` (that one reads only the system setting, once): `useReducedMotion()` is every animation off (Disabled or the system's reduced motion) and keeps gating one-shots, `useIdleStill()` is nothing-on-its-own (Reduced, Disabled or the system) and gates every loop, twinkle, shine and bobbing cue. `useLoopClock` and `useMotionBudget` apply the level themselves, so Shrodi, teachers, scene figures, fireflies, the chest glow and burst sizes follow it with no extra code; at Disabled `app/_layout.tsx` also mounts Reanimated's `ReducedMotionConfig` so `reduceMotion: System` animations (entering and exiting layout animations, `withTiming`) stop. A new decorative loop must be gated with `useIdleStill()` (or `useLoopClock`), a new one-shot with `useReducedMotion()`. The tour is not affected: it has no animation.

- **Crash prompt:** a JS app cannot see its own crash, so `services/crash-guard.ts` (rules in the framework-free `crash-guard-core.ts`, `test:crash-guard`, state in `STORAGE_KEYS.CRASH_GUARD`) keeps a flag that is true while the app is in front and false once it goes to the background; a start that finds it still true means the last session ended in front (a native crash, a memory kill, a freeze), and `components/crash/CrashPrompt.tsx` (mounted in `app/_layout.tsx`) then offers, once per crash and a moment after start, "Run smoother?": Reduced after a first crash on Max, Disabled after two in two weeks or when Reduced did not hold, nothing once Disabled. Any answer or the X marks that crash answered. A development build does not trust the flag (a reload looks like a crash): the perf probe's "Pretend the app crashed" button makes the next start count as one, and `EXPO_PUBLIC_CRASH_PROMPT=1` turns the real detection on in dev. Nothing leaves the phone.
