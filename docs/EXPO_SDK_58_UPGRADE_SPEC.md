# AtomIQ — Latest Expo SDK Upgrade Specification

**Status:** Draft for implementation  
**Date:** 2026-11-07  
**Owner:** AtomIQ engineering  
**Current baseline:** Expo SDK 54 / React Native 0.81.5 / React 19.1 / Expo Router 6  
**Target baseline:** Expo SDK 58 / React Native 0.88 / React 19.3 / Expo Router `~58.0.30`  
**Scope:** Managed/CNG Android, iOS, and web builds

## 1. Decision

Upgrade AtomIQ incrementally from SDK 54 to the latest stable Expo SDK 58:

```text
SDK 54 → SDK 55 → SDK 56 → SDK 57 → SDK 58
```

Do not perform a single 54-to-58 dependency jump. Expo recommends upgrading one SDK at a time so regressions can be isolated. SDK 58 is the current stable release as of this specification and targets React Native 0.88, React 19.3, Android API 36, and iOS 16.4+. See the [Expo SDK reference](https://docs.expo.dev/versions/latest/) and [SDK 58 release notes](https://expo.dev/changelog/sdk-58).

This document is a migration contract, not permission to change dependencies immediately. Implementation should happen on a dedicated branch with a checkpoint commit after every SDK hop.

## 2. Why this upgrade is needed

- The project is on SDK 54, which is no longer the current Expo release.
- Android beta testing is already exposing layout and UI/UX issues; the upgrade must not introduce another unverified native layer.
- SDK 58 includes the current React Native, Expo Router, Android build, iOS lifecycle, and tooling updates needed for supported release builds.
- The upgrade gives the team a supported baseline for future Android/tablet hardening and subsequent Expo upgrades.

## 3. Current repository baseline

The project is a managed/CNG app: no committed `android/` or `ios/` directories are present. Native projects are generated by Expo/EAS from `app.json` and installed config plugins.

Current relevant configuration:

- `newArchEnabled: true`
- `orientation: "portrait"`
- `ios.supportsTablet: true`
- `android.edgeToEdgeEnabled: true`
- `android.softwareKeyboardLayoutMode: "resize"`
- `web.output: "static"`
- Expo config plugins for Router, splash screen, fonts, SQLite, web browser, assets, and audio
- Local SQLite content database and AsyncStorage-backed app state
- Reanimated, Gesture Handler, SVG, image, audio, haptics, speech, and custom font usage
- Custom tab bar and global UI sound handling

The following existing work must remain functional after the upgrade:

- onboarding and profile editing;
- Home, Discovery, Guide, Games, and Profile tabs;
- lessons, quizzes, MythBuster, Lab, Explorer, Atom Maze, encyclopedia, and article detail;
- local database seeding and content versioning;
- TTS, SFX, haptics, themes, deep links, external links, and Android back handling;
- static web export.

## 5. Scope and non-goals

### In scope

- SDK, React Native, React, Expo Router, and Expo module alignment;
- TypeScript and navigation migrations required by SDK 55–58;
- Android/iOS native regeneration through CNG/EAS;
- web static export compatibility;
- release build and runtime verification;
- update of project documentation and minimum tool requirements.

### Out of scope

- Redesigning the app’s visual language;
- changing the app’s data model or content schema;
- replacing SQLite, AsyncStorage, TTS, or audio architecture unless the upgrade proves a compatibility blocker;
- adding native tabs, Expo UI, widgets, App Intents, server rendering, or new SDK 58 features;
- enabling landscape orientation;
- changing the public Android package ID or iOS bundle identity.

## 6. Migration principles

1. Upgrade one SDK version at a time.
2. Keep the app behaviorally unchanged unless a breaking API requires a change.
3. Use Expo’s package resolver for Expo-managed dependencies.
4. Treat TypeScript errors and `expo-doctor` warnings as migration work, not noise.
5. Regenerate native projects only from a clean, reproducible config.
6. Verify Android release behavior before declaring an SDK hop complete.
7. Do not ship SDK 58 JavaScript to an SDK 54 native binary through an OTA update.

## 8. Phase 1 — Incremental SDK hops

For each hop, use the same sequence and create a checkpoint commit only after the gates pass.

```bash
npx expo install expo@^55.0.0 --fix
npx expo-doctor@latest
npm run typecheck
npm run lint
```

Repeat with `^56.0.0`, `^57.0.0`, and finally `^58.0.0`.

At each hop:

- review the matching Expo release notes;
- run `npx expo install --fix` for Expo-managed packages;
- inspect the lockfile for duplicate React/React Native versions;
- clear Metro cache before visual verification;
- run the app in a development build, not only Expo Go;
- build and install an Android preview binary;
- commit the working checkpoint before starting the next hop.

Use the [official Expo upgrade walkthrough](https://docs.expo.dev/workflow/upgrading-expo-sdk-walkthrough/) as the canonical command sequence.

## 9. Phase 2 — Required source migrations

### 9.1 Expo Router and React Navigation imports — P0

SDK 56+ no longer supports application imports from external `@react-navigation/*` packages in the same way. The current repo has direct imports in:

- `app/_layout.tsx` — `DarkTheme`, `DefaultTheme`, and `ThemeProvider`;
- `app/(tabs)/chat.tsx` — `useNavigation`;
- `app/(tabs)/leaderboard.tsx` — `useFocusEffect`;
- `app/(tabs)/_layout.tsx` — `BottomTabBarProps` type.

Migration requirements:

- Replace direct application-level React Navigation imports with supported `expo-router` APIs or the documented Expo Router integration for the specific use case.
- Preserve the existing custom tab bar behavior, route names, active state, and Guide chat tab hiding.
- Keep `useNavigation` only where navigator-specific events/options are genuinely required; otherwise prefer `useRouter`, `usePathname`, `useSegments`, or other Expo Router hooks.
- Audit all route navigation that passes nested `screen`, `params`, or `initial` objects. SDK 58 requires complete hrefs for nested navigation in affected cases.
- Audit all `initialRouteName` usage. Move deep-link back destinations to `unstable_settings.anchor` where required.
- Confirm every intended tab screen is explicitly declared in the tabs layout.

Use the [SDK 57→58 Expo Router migration guide](https://docs.expo.dev/router/migrate/sdk-57-to-58/) for exact API replacements.

### 9.2 React Native Strict TypeScript API — P0

SDK 58 makes the Strict TypeScript API the default.

Search for and remove or migrate:

- deep imports from `react-native/Libraries/*`;
- old ref types that should use instance types such as `ViewInstance` or `TextInputInstance`;
- assumptions about navigation state fields that are now optional or reshaped;
- React Native types imported indirectly from removed compatibility surfaces.

The temporary `react-native-legacy-deep-imports` condition may be used only as a time-boxed unblocker. The target state is a clean strict TypeScript build without the opt-out.

### 9.3 Removed or deprecated React Native APIs — P0/P1

Audit every route and shared service for:

- `InteractionManager` → `requestIdleCallback` or an explicit scheduling alternative;
- root `Touchable` export and related types;
- `Modal animated` prop;
- removed `StatusBar` props such as `backgroundColor`, `translucent`, and `networkActivityIndicatorVisible`;
- `ImageBackground` usage, replacing it with a `View` and absolutely positioned `Image` where needed.

The current code uses `Modal` and extensive `TouchableOpacity` usage, plus a global UI SFX patch in `services/ui-sfx.ts`. Verify that the patch does not depend on removed `defaultProps` behavior or private React Native implementation details. Prefer explicit shared pressable wrappers if the patch becomes unstable.

### 9.4 Expo Router web output — P1

The current app explicitly uses `web.output: "static"`. Preserve static output unless the product intentionally chooses server rendering.

Target configuration decision:

- Keep `web.output: "static"`.
- Set `apiRoutes: false` explicitly unless the project adds API routes or server middleware.
- Do not enable server rendering as part of this upgrade.
- Review whether async web routes affect the existing static export; disable them only if the app relies on a custom Suspense fallback or a specific synchronous-loading behavior.
- Run a production web export and inspect generated routes after every Router migration.

Expected config shape, subject to validation during implementation:

```json
{
  "expo": {
    "web": {
      "output": "static"
    },
    "plugins": [
      ["expo-router", { "apiRoutes": false }]
    ]
  }
}
```

Read the [SDK 58 Router migration guide](https://docs.expo.dev/router/migrate/sdk-57-to-58/) and [static rendering guide](https://docs.expo.dev/router/web/static-rendering/) before finalizing this config.

### 9.5 File system and SQLite — P1

The content database is a critical offline-first path.

- Preserve the current content database version marker and integrity checks.
- Verify fresh install, upgrade install, stale marker, corrupted database, airplane mode, and low-storage behavior.
- The current content database service intentionally imports `expo-file-system/legacy`; do not migrate it opportunistically during the SDK upgrade unless the target package removes or breaks the legacy entry point.
- If migrating to modern `expo-file-system` APIs later, account for SDK 58’s async `File.write()` behavior and use `File.writeSync()` only where synchronous behavior is explicitly required.
- Confirm no libSQL configuration or removed `useLibSQL` option is present.
- Re-run `node scripts/sync-content.js` and verify the bundled database is unchanged except for an intentional content update.

### 9.6 Reanimated, Worklets, gestures, and animations — P1

The app uses Reanimated 4, Gesture Handler, and Worklets heavily in Guide, games, tab navigation, and lesson UI.

- Install the SDK-compatible versions through `npx expo install --fix`.
- Confirm the Babel/Metro configuration remains valid.
- Verify animations on New Architecture Android and iOS builds.
- Test reduced-motion paths and screen unmount cleanup.
- Test tab press feedback, mascot animation, game transitions, modal entry/exit, and gesture-driven interactions on a low-end Android device.
- Watch for Hermes memory or startup regressions in a 30-minute soak.

### 9.7 iOS 27 scene lifecycle and orientation — P1

SDK 58 adds iOS 27 scene-based lifecycle support. This repo has no committed native iOS directory or custom AppDelegate, so the risk is lower, but it still needs validation because the app declares portrait orientation and iPad support.

- Generate an SDK 58 iOS development build and test cold launch, background/foreground, deep link launch, and external link return.
- Validate iPad behavior and any resizable iOS 27 window behavior.
- Confirm the product’s portrait-only decision remains acceptable on supported iPad/iOS 27 devices.
- Do not add `ios.enableSceneSupport` manually; SDK 58 handles scene support during prebuild.

### 9.8 Android release builds and R8 — P0/P1

SDK 58 enables R8 minification in Android release builds by default.

- Build the preview APK and production AAB with minification enabled.
- Verify fonts, SQLite, images, SVGs, audio, TTS, haptics, deep links, and route loading in the minified build.
- Check for reflection-related failures in Expo modules and third-party libraries.
- Add narrowly scoped keep rules only if a real release-build failure proves they are needed.
- Do not disable R8 globally without documenting the reason, size/performance impact, and follow-up owner.

## 11. Verification matrix

### Build and tooling

- `npm install` from a clean checkout;
- `npx expo-doctor@latest` has no unresolved migration warnings;
- `npm run typecheck` passes without the strict API opt-out;
- `npm run lint` passes or remaining warnings are explicitly triaged;
- `npx expo config --type public` resolves successfully;
- preview APK and production AAB build successfully;
- iOS development/release-like build succeeds;
- `npx expo export --platform web` succeeds;
- lockfile contains one intended React and React Native version.

### Runtime flows

Test on physical Android phone, Samsung/OEM Android phone, Android tablet, iPhone, and iPad where available:

- cold start, warm start, background/foreground, and force-quit relaunch;
- onboarding and profile editing;
- every tab and custom tab-bar state;
- Guide landing/chat and hidden-tab-bar restore;
- lesson start, progress, completion, and back behavior;
- quiz, MythBuster, Lab, Explorer, Atom Maze, and result states;
- SQLite first-run seed, existing-user upgrade, offline mode, and corrupted-content recovery;
- TTS available/unavailable/interrupted;
- sound and haptics enabled/disabled;
- light, dark, and system themes;
- deep links, modal dismissal, Android back, and external link return;
- keyboard behavior on onboarding and profile;
- Android gesture and three-button navigation;
- font scale 1.3 and 2.0;
- tablet portrait layout and iPad support;
- 30-minute navigation/game/content soak.

### Web

- static export includes expected route HTML/assets;
- no unexpected server bundle is required;
- app is interactive after hydration;
- direct URL navigation works for representative routes;
- no `+html.tsx` or metadata behavior is broken by the Router migration;
- safe-area CSS and responsive layout remain valid if web is still supported.

## 12. Rollout plan

### Stage 1 — Internal development build

Use the SDK 58 development build for engineering and QA. Do not use Expo Go as the only verification surface. Expo Go availability may lag a newly released SDK, and production apps should use development builds for reliable native validation.

### Stage 2 — Android closed testing

Upload the SDK 58 AAB to the closed testing track. Verify the Google Play-installed binary, not only a locally sideloaded APK.

### Stage 3 — iOS TestFlight/internal distribution

Validate iOS lifecycle, portrait behavior, iPad layout, speech/audio, and background/foreground transitions.

### Stage 4 — staged production rollout

Proceed only when all P0/P1 issues are closed:

```text
10% → 50% → 100%
```

Hold at 10% long enough to observe crash-free behavior and Android layout feedback before widening.

## 13. Rollback strategy

- Every SDK hop has a checkpoint commit.
- If the target hop fails, revert to the previous checkpoint instead of mixing fixes from multiple SDK versions.
- If a native SDK 58 binary has shipped, do not send SDK 54 JavaScript through an OTA update to that binary.
- If R8 causes a release-only failure, reproduce with the minified preview build, add the smallest verified keep rule, and rebuild.
- If Router migration changes navigation state, compare deep links and back behavior against the pre-upgrade baseline before changing app logic.

## 14. Severity and exit criteria

### P0 — must block release

Build failure, crash, ANR, broken native module, data loss, broken launch, broken navigation root, or a production AAB that cannot load core content.

### P1 — must block beta sign-off

Broken Android/tablet layout, broken back/keyboard behavior, SQLite seeding failure, TTS/audio/haptics regression, failed deep link, or web export failure.

### P2 — can follow after release

Minor warning, non-blocking deprecation, small visual drift, or optional optimization with no user-facing regression.

### Definition of done

The upgrade is complete when:

- the project runs on SDK 58 with aligned Expo-managed dependencies;
- strict TypeScript checks pass without compatibility opt-outs;
- all direct React Navigation and Router migration issues are resolved;
- Android R8 release builds pass on physical devices;
- iOS/iPad and Android/tablet flows pass the verification matrix;
- local SQLite content and offline behavior are unchanged;
- static web export passes;
- no P0/P1 issues remain;
- documentation and release metadata identify SDK 58 as the supported baseline;
- the release candidate is installed from the relevant internal distribution channels and verified end-to-end.
